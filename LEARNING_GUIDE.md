## Part 1: What is FastAPI?

**Mental model:** FastAPI is a Python web framework. It turns Python functions into HTTP endpoints that anyone can call over the internet.

**Analogy:** Think of it like a restaurant menu.
- You have kitchen functions (`parse_rawlog`, `watchdog`) — these are the chefs
- FastAPI is the waiter — takes orders from customers (HTTP requests), passes them to the kitchen, returns the dishes (HTTP responses)
- The menu with prices/docs is auto-generated by FastAPI — that's the `/docs` page

**Why FastAPI for this project:**
- Your pipeline is already Python — no rewriting
- Auto-generated API docs at `/docs` — interviewers love this
- Type hints + Pydantic = validation for free
- Lighter than Django for a thin API layer

## Part 2: Your `app.py` Line by Line

### Imports (lines 1-11)
```python
from fastapi import FastAPI, HTTPException
```
- `FastAPI` = the application object (the waiter)
- `HTTPException` = way to return errors with proper status codes (404, 500, etc.)

```python
from pydantic import BaseModel
```
- Pydantic validates incoming data. If someone sends bad JSON to `/sessions`, Pydantic catches it before your code runs.

```python
from typing import Optional, List
```
- Type hints only. No runtime cost. Makes code readable.

```python
import sys, os as _os
sys.path.insert(0, _os.path.join(_os.path.dirname(__file__), "fac10sniffer"))
```
**This is the trickiest line.** Here's why it exists:
- Your existing modules (`connection.py`, `parser.py`) live in `fac10sniffer/` folder
- When you run `python parser.py` from inside `fac10sniffer/`, it works
- When you run `uvicorn app:app` from repo root, Python's import system can't find `fac10sniffer.parser`
- `sys.path.insert(0, ...)` prepends `fac10sniffer/` to the module search path
- So `from parser import parse_rawlog` works from `app.py`

**Without this line:** `ModuleNotFoundError: No module named 'parser'`


These are YOUR existing pipeline modules. `app.py` is just a thin wrapper around them.


Creates the application instance. The strings become the API docs title.

### Endpoints (lines 45-208)

**Pattern every endpoint follows:**
1. Define the route with decorator: `@app.get("/health")` or `@app.post("/parse")`
2. Function receives params (path params, query params, request body)
3. Function calls your existing pipeline code
4. Return a dict — FastAPI converts it to JSON automatically
5. If something breaks, `raise HTTPException(status_code=500, detail=str(e))`

**GET vs POST:**
- `GET` = safe, read-only, params go in URL (`/sessions?src_ip=1.2.3.4`)
- `POST` = triggers action, params go in request body (`/ingest`, `/parse`, `/alerts`)

**Why `/ingest` returns 501 inside Docker:**
```python
try:
    from systemd import journal
except ImportError:
    raise HTTPException(status_code=501, ...)
```
`python-systemd` is an Arch Linux package. It doesn't exist in Debian-based Docker images. So `/ingest` gracefully fails with "not implemented" rather than crashing. On a real Linux host with systemd, this works.

## Part 3: Docker from Zero

### What problem does Docker solve?

**Without Docker:** "It works on my machine" — deploy to Render and it breaks because dependencies, OS, Python version differ.

**With Docker:** You ship the entire environment — OS, Python, packages, config — as one image. Runs identical everywhere.

### Mental model: Docker = shipping container for code

- **Image** = blueprint (frozen filesystem + instructions)
- **Container** = running instance of an image
- **Dockerfile** = the recipe to build the image
- **docker-compose.yml** = orchestration for multiple containers (your app + Postgres)

## Part 4: Your `Dockerfile` Line by Line

```dockerfile
FROM python:3.11-slim
```
Base image = official Python 3.11 on Debian Slim. This is your starting OS.

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    libsystemd0 \
    && rm -rf /var/lib/apt/lists/*
```
`RUN` = execute this shell command during image build.
- `gcc` = compiler needed because some Python packages need C compilation
- `libsystemd0` = systemd C library. `python-systemd` wrapper needs this at runtime
- `rm -rf /var/lib/apt/lists/*` = clean up package cache to shrink image size

```dockerfile
WORKDIR /app
```
Sets the working directory inside the container. All subsequent commands run here.

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
```
Copy requirements first, install them. Docker caches layers — if requirements don't change, it skips reinstall on rebuilds.

```dockerfile
COPY . .
```
Copy the entire repo into `/app`.

```dockerfile
ENV DB_HOST=${DB_HOST:-db}
```
Environment variables. `${DB_HOST:-db}` means: use `DB_HOST` if provided, otherwise default to `db` (the docker-compose service name).

```dockerfile
EXPOSE 8000
```
Documents that the app listens on port 8000. Doesn't actually open the port — that's docker-compose's job.

```dockerfile
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```
The command to run when container starts. `app:app` = Python module `app`, object `app` inside it.

## Part 5: `docker-compose.yml` Line by Line

```yaml
services:
```
Docker Compose manages multiple containers. Each service is one container.

```yaml
  api:
    build: .
```
Build the `api` container from the Dockerfile in current directory.

```yaml
    ports:
      - "8080:8000"
```
Host port 8080 → container port 8000. `host:container`.

```yaml
    environment:
      - DB_HOST=db
```
Set env vars inside the container. `db` is the other service's name — Docker's internal DNS resolves it.

```yaml
    depends_on:
      - db
```
Start `db` before `api`. Doesn't wait for DB to be ready — just start order.

```yaml
  db:
    image: postgres:16-alpine
```
Use official Postgres 16 image. No build needed.

```yaml
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/schema.sql:/docker-entrypoint-initdb.d/schema.sql
```
Two volumes:
1. `pgdata` = named volume for data persistence
2. Bind mount `schema.sql` into the init directory — Postgres runs it automatically on first boot

```yaml
volumes:
  pgdata:
```
Named volume definition.

## Part 6: How to Run It

```bash
# Start everything
docker compose up --build

# Stop everything
docker compose down

# Stop and DELETE data (use carefully)
docker compose down -v
```

## Part 7: How to Deploy to Render/Railway

**Render path:**
1. Push repo to GitHub
2. Create new Web Service on Render
3. Connect GitHub repo
4. Render auto-detects `Dockerfile`
5. Add environment variables: `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASS`, `GROQ_API_KEY`
6. Deploy — Render gives you a public URL

**No Docker needed on Render** — they build the image for you.
